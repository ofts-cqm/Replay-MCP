# Spatial Observation Scope: Multiresolution Surface and Volume Maps

Status: **implemented with automated Java/TypeScript coverage and real-client
bridge/sidecar smoke acceptance; the representative performance suite, complex
volume fixtures, and agent-efficiency benchmark remain pending**

This document records the finalized scope contract for a low-cost structured
spatial observation capability in Replay MCP and is ready for execution-agent
handoff. Nothing described here should be marked implemented in
`ARCHITECTURE.md` until the implementation, automated checks, and applicable
live acceptance have actually completed.

## 1. Problem statement

Replay MCP currently gives an agent two main ways to understand a Minecraft
scene:

1. framebuffer observations, which convey appearance but consume substantial
   vision context and do not directly identify exact world coordinates; and
2. structured queries, which provide precise state but currently expose only a
   small nearby block snapshot rather than a true regional spatial overview.

During scouting, an agent can consequently spend many calls capturing images
from different positions simply to learn the terrain, locate a building, or
estimate where to place a player or replay camera. This is slow, token-heavy,
and still imprecise because perspective images are a poor coordinate map.

The desired capability is a fast structured overview that lets the agent:

- inspect a bounded, already-loaded region without moving the player or camera;
- locate likely terrain, structures, voids, ceilings, platforms, and other
  spatial features inside explicit world-coordinate regions;
- begin with a coarse representation and progressively refine only promising
  regions; and
- reserve screenshots for appearance, composition, occlusion, and final visual
  verification.

The main objective is not per-block navigation or recovery of one uniquely
correct camera coordinate. It is to reduce large-scale spatial uncertainty
enough for the agent to identify the structure, choose a plausible camera
region, and then use one or a small number of visual observations to compose
the shot. Several-block visual adjustments are acceptable when they produce a
good, validated camera pose.

This capability complements screenshots. It does not replace them.

## 2. Current architectural fit and implementation gap

The proposal follows existing Replay MCP principles:

- visual frames and structured game state are both first-class;
- read-only observations do not require the director lease;
- queries must not load arbitrary distant chunks;
- the bridge exposes bounded primitives while workflow policy stays in the
  Replay Director skills; and
- capability negotiation must truthfully describe support and limits.

The current public `game_query` tool is the natural public entry point because
it already promises precise bounded state without capturing an image. However,
its current implementation does not perform a true regional block query:

- the bridge handles `observation.query` by producing the ordinary snapshot;
- that snapshot gathers non-air blocks only in a 17 by 9 by 17 neighborhood
  centered on the player (`x/z +/- 8`, `y +/- 4`); and
- the sidecar filters those already-returned nearby blocks against the supplied
  query bounds.

Therefore, passing larger bounds today does not inspect the requested loaded
region. A spatial map must be generated by a dedicated Minecraft-side sampler,
not by filtering the existing snapshot.

## 3. Design conclusion

The design is one multiresolution spatial observation capability with two
representations:

| Representation | Purpose | Expected use |
| --- | --- | --- |
| `surface` | Compact two-dimensional surface/elevation summary | Default scouting for ordinary terrain and buildings |
| `volume` | Coarse-to-fine three-dimensional occupancy summary | Nether, caves, floating structures, overhangs, hollow or vertically complex buildings |

The `surface` representation remains important even if `volume` exists. It is
cheaper to compute, smaller to return, and easier for an agent to reason over.
The `volume` representation is a deliberate fallback when the one-surface
assumption is invalid or ambiguous.

A naive dense three-dimensional voxel dump is not recommended. Its cost grows
cubically, can freeze the client if scanned carelessly, and can consume more
model context than the screenshots it is intended to avoid.

## 4. Proposed public and bridge shape

The preferred public shape is an additional `game_query` kind rather than a
new top-level MCP tool:

```json
{
  "kind": "spatial_map",
  "representation": "surface",
  "bounds": {
    "min_x": -256,
    "max_x": 256,
    "min_y": 40,
    "max_y": 161,
    "min_z": -256,
    "max_z": 256
  },
  "cell_size": 16,
  "surface_mode": "world_surface"
}
```

The private bridge primitive is:

```text
observation.spatial_map
```

This keeps the public MCP surface at its current tool count while giving the
Minecraft process responsibility for reading and aggregating Minecraft state.
The sidecar remains responsible for schema validation, capability checks,
error translation, concise text, and structured output.

The public contract uses `game_query` with `kind: "spatial_map"` and a required
`representation: "surface" | "volume"` discriminator. Separate `heightmap`
and `voxel_map` query kinds are rejected because they would duplicate bounds,
alignment, coverage, palette, limit, and capability concepts.

## 5. Common query contract

### 5.1 Inputs

Common inputs:

- `instance_id`: optional target instance, following existing read-tool rules;
- `representation`: `surface` or `volume`;
- `bounds`: finite integer `min_x`, `max_x`, `min_y`, `max_y`, `min_z`, and
  `max_z` values;
- `cell_size`: a supported power-of-two aggregation size for the selected
  representation;
- representation-specific options; and
- optional requested detail fields where omitting a field can materially reduce
  work or response size.

Ordinary cell sizes for both representations are:

```text
4, 8, 16, 32
```

Sizes 8 through 32 support cheap overview and structure identification. Size 4
supports tighter surroundings, interiors, overhangs, and approximate camera
clearance before visual refinement. Per-block precision is not a goal of the
ordinary spatial-map workflow.

Both representations additionally support resolution level `2` as explicitly
exceptional fallback extensions: `2x2` for surface and `2x2x2` for volume.
Neither is part of the normal coarse-to-fine sequence, and neither should be
selected merely because a smaller cell size is available. Sections 6.7 and 7.5
define their intended uses and restrictions. Cell size `1` is outside the
initial scope for both representations.

Every successful spatial-map response includes an opaque `map_id`. A level-2
request additionally requires:

- `refines_map_id`: a recent size-4 map from the same sidecar session,
  instance, dimension, representation, and replay time where applicable, whose
  effective bounds contain the level-2 request; and
- `fallback_reason`: `unresolved_surface_boundary` or `adjacent_surfaces` for
  surface mode, and `tight_clearance`, `thin_geometry`, or `adjacent_volumes`
  for volume mode.

The sidecar validates this metadata before calling the bridge and writes it to
the existing audit trace. This enforces a size-4-first workflow without adding
an unrestricted `other` reason.

### 5.2 Coordinate semantics

The coordinate convention is half-open block bounds:

```text
[min_x, max_x) x [min_y, max_y) x [min_z, max_z)
```

For example, `min_y: 40, max_y: 161` includes block Y coordinates 40 through
160. Half-open bounds avoid double-counting when adjacent requests tile a
region.

Cells should be aligned to a stable world-coordinate grid. If requested bounds
are not aligned to `cell_size`, the implementation expands them outward to
multiples of `cell_size` using mathematical floor division for negative
coordinates. It returns both requested and effective bounds. Bounds expansion
still counts against every size and work limit.

Every response must define:

- grid origin;
- cell size;
- grid dimensions;
- X, Y, and Z traversal order;
- requested and effective bounds; and
- the formula or explicit absolute bounds that map every returned cell to world
  coordinates.

Surface rows are ordered by increasing Z and cells within a row by increasing
X. Volume columns use increasing Z then increasing X, and their vertical runs
use increasing Y. These orders are fixed contract behavior rather than an
implementation choice.

### 5.3 World identity and freshness

Every response includes:

- current dimension;
- game tick or a start/end tick range;
- replay time when a replay world is active;
- whether the result was captured atomically or over multiple ticks; and
- the active instance ID.

The primitive is available in `live_idle` and `live_recording` modes and in a
loaded, paused replay. A playing replay returns a typed `conflict` with reason
`replay_must_be_paused`; loading and rendering modes return `invalid_mode`.
The query itself remains lease-free, although pausing a playing replay follows
the existing lease-protected playback contract. Responses from replay mode
include the paused `replay_time_us`.

### 5.4 Loaded-area behavior

Spatial queries must inspect already-loaded client chunks only. They must not:

- request server-side world data outside the client view;
- generate or load chunks;
- move or teleport the player/camera to make chunks load; or
- treat an unavailable chunk or section as air.

Partial coverage is represented explicitly. A response has loaded,
empty, and unavailable states that cannot be confused with each other.

The default is to return useful loaded results plus explicit coverage metadata.
`require_complete` is an optional boolean with default `false`. When `true`,
any unavailable cell produces a typed `outside_loaded_area` conflict containing
the unavailable bounds; it must not return a map that appears complete.

### 5.5 Control and side effects

The query is:

- read-only;
- lease-free;
- non-destructive;
- free of framebuffer capture and image artifact creation; and
- subject to ordinary deadlines and cancellation.

## 6. Surface representation

### 6.1 Purpose

The surface representation provides a low-cost two-dimensional grid over X/Z.
For every underlying block column, the sampler finds the highest qualifying
surface within the requested Y range. It then aggregates those column results
into larger cells.

The Y range is meaningful. It allows a caller to focus on a vertical band
rather than always accepting the globally highest block. This can help separate
layers, but it also makes the scan more expensive than reading only a cached
global heightmap.

### 6.2 Surface modes

The supported surface modes are:

- `world_surface`: the highest non-air surface in the requested Y range,
  suitable for visible silhouettes; and
- `motion_blocking_no_leaves`: a solid/motion-blocking surface that ignores
  leaves and much decorative noise, suitable for ground and structure scouting.

`motion_blocking_no_leaves` is the default. Both public modes follow the active
Minecraft version's native heightmap predicate of the corresponding name;
version-specific API mappings must be verified during implementation rather
than approximated with an independent block allowlist. This makes the treatment
of fluids, foliage, plants, snow, fences, slabs, and other partial blocks part
of Minecraft's predicate rather than Replay MCP guesswork.

For each block column, the sampler finds the topmost qualifying block whose
block Y lies inside the requested half-open Y range. It does not clamp or merely
filter the global top surface. `surface_y` is the first block coordinate above
that qualifying block. A native cached heightmap may be used only when it is
provably equivalent for the requested range; otherwise the sampler scans the
bounded range using chunk-section skips where available. No qualifying block
produces a null/empty column rather than a fabricated height.

### 6.3 Required height statistics

An average alone is insufficient. A narrow tower occupying a few columns in an
otherwise flat cell can average down until it becomes indistinguishable from
the ground.

Each populated surface cell therefore returns:

```text
minimum surface Y
mean surface Y
maximum surface Y
```

The difference between maximum and minimum exposes relief, rooflines, cliffs,
walls, towers, and other anomalies. Mean surface Y is rounded to one decimal
place; minimum and maximum remain integer surface coordinates.

### 6.4 Surface block composition

The surface map includes the most common **surface block**, not the most
common block in the entire three-dimensional cell.

Counting the full cell volume would cause stone, dirt, or netherrack to dominate
nearly every result and conceal visible building materials. Instead:

1. determine the block that produced each underlying column's surface;
2. count those surface-producing block IDs within the aggregate cell; and
3. return the dominant surface block and its share of valid surface columns.

`dominant_share` is essential. A cell that is 98 percent grass is different
from one that is 52 percent grass and 45 percent stone bricks, even though both
have the same dominant block.

Required default material fields are:

- dominant surface block palette index; and
- dominant share.

`material_mix_limit` accepts `1`, `2`, or `3` and defaults to `1`. Values `2`
and `3` return the corresponding top surface block IDs and shares for explicit
refinement. All material results use one response-wide palette so repeated
names do not consume tokens in every cell.

Replay MCP does not label a cell `natural` or `constructed`. Exact block IDs,
shares, and geometry are objective evidence. A semantic classification would
be unreliable for stone mountains, grass roofs, woodlands, unusual styles, and
modded blocks.

### 6.5 Illustrative compact cell

Conceptually, a compact surface cell can be represented as:

```text
[min_surface_y, mean_surface_y, max_surface_y,
 dominant_block_palette_index, dominant_share]
```

With optional material refinement:

```json
{
  "height": [64, 66.1, 91],
  "dominant_surface_block": 0,
  "dominant_share": 0.68,
  "surface_mix": [[0, 0.68], [1, 0.27], [2, 0.05]]
}
```

The object form above is explanatory, not a decision to emit one verbose JSON
object per cell.

### 6.6 Known limitations

Even with material composition, a surface map cannot faithfully represent:

- Nether floor/ceiling relationships;
- caves and interiors;
- floating platforms above other terrain;
- overhangs and bridges;
- multiple disconnected surfaces in one column;
- hollow structures;
- façades beneath a roof; or
- an inverted structure hidden by its top surface.

These are information-theoretic limitations of a one-surface representation,
not bugs that can be fixed by another average.

### 6.7 Exceptional `2x2` fallback extension

Surface cell size `2` is supported when a tightly bounded `4x4` result
still merges nearby surface features that materially affect structure
identification or camera-region selection. Examples may include a narrow
roofline, a small gap between adjacent surfaces, or a structure edge whose
location remains ambiguous at size 4.

This is not an ordinary final step. A `2x2` cell aggregates only four columns,
so its token advantage over fine structured surface data is limited and a
screenshot may provide more useful composition information. The fallback must
therefore use the Section 8 fallback limits, be advertised separately from
ordinary surface sizes, and supply the required size-4 `refines_map_id` and
surface `fallback_reason`.

Cell size `1` is not a further surface-map refinement. Once size 2 or 4 has
identified a sufficient camera region, screenshots should determine the actual
camera pose.

## 7. Volume representation

### 7.1 Purpose

The volume representation is the structured fallback for dimensions and scenes
where a heightmap loses essential geometry. It divides the requested region
into cubic cells of `cell_size` blocks and reports coarse occupancy that can be
refined recursively by subsequent queries.

It is intended to handle cases such as:

- a Nether cavern with both floor and ceiling;
- a floating one-block-thick grass platform;
- a reversed pyramid with grass on top;
- hollow or multi-level buildings;
- caves, tunnels, bridges, and overhangs; and
- vertically stacked or disconnected structures.

### 7.2 Conservative aggregation

Coarse aggregation must not sample only one representative voxel. Point
sampling can entirely miss a thin platform or wall.

For every aggregate cube, the implementation should inspect the complete cube
or use equivalent exact chunk-section summary data. Partial blocks are counted
conservatively as solid when they satisfy Minecraft's motion-blocking/collision
predicate; fluids are counted separately. The cube state is:

- `empty`: every underlying voxel is air/non-occupying;
- `full_solid`: every underlying voxel is qualifying solid geometry;
- `full_fluid`: every underlying voxel is fluid and none is solid; or
- `mixed`: any other combination of air, solid geometry, and fluid.

A mixed cell returns at least:

- solid fraction;
- fluid fraction where applicable;
- exact absolute bounds; and
- exposed-material information when at least one exposed solid face exists.

A one-block-thick platform inside a 32-cubed cell may have a very small solid
fraction, but the cell must remain `mixed`. No density threshold may silently
convert non-empty geometry to air.

### 7.3 Materials in volume mode

The most common block across the full volume is usually the wrong signal. In a
Nether region it will often be netherrack; in an Overworld region it will often
be stone or dirt, regardless of the visible structure.

Volume material information uses the dominant **exposed** block rather than the
most common block in the full cube. It includes the dominant share and uses the
same response-wide block palette as surface mode.

Volume mode always returns the dominant exposed solid block and its share when
the cell has an exposed solid face. An exposed face is one of the six orthogonal
block faces whose neighbor does not satisfy the solid occupancy predicate;
fluid neighbors therefore expose the solid face while remaining represented by
`fluid_fraction`. The sampler may inspect a one-block halo outside the requested
bounds only when that halo is already loaded. An unavailable halo face is
reported as unknown and is excluded from the material denominator, never
treated as exposed air.

Volume mode uses the same `material_mix_limit: 1 | 2 | 3` option and default of
`1` as surface mode. Shares are counted by exposed block-face area, not by total
solid-block volume.

### 7.4 Model-facing encoding

A deeply nested dense `x[y[z]]` JSON array is not recommended. Even moderate
grids become large and difficult for an agent to map back to coordinates.

The model-facing encoding is absolute-coordinate vertical runs grouped
by coarse X/Z cell. Empty space can be implicit, while occupied and mixed
intervals remain explicit:

```json
{
  "x": 32,
  "z": -16,
  "runs": [
    [40, 64, "full"],
    [96, 104, "mixed", 0.18],
    [104, 128, "full"]
  ]
}
```

Each column record contains absolute half-open X/Z cell bounds followed by
absolute half-open Y runs. A run contains state, solid fraction, fluid fraction,
dominant exposed-material palette index/share when present, and optional top
material mix. Adjacent cells may merge into one run only when their state and
reported aggregate values are identical after documented rounding.

Fully loaded empty intervals are implicit. Unavailable intervals are never
implicit; they are returned separately as absolute `unavailable_boxes`. An
omitted interval therefore means empty only when the enclosing column is marked
fully loaded.

This representation naturally expresses a Nether floor, empty cavern, floating
platform, and ceiling without listing every empty voxel. Dense three-dimensional
arrays, sparse unordered voxel tuples, and adaptive octrees are excluded from
the initial contract because they either waste context or make coordinate
reasoning less reliable for the model.

### 7.5 Exceptional `2x2x2` fallback extension

Volume cell size `2` is supported as a fallback extension for unusually
tight geometry where a `4x4x4` result remains materially ambiguous. Potential
examples include a narrow interior, doorway-scale clearance, a thin passage,
or two nearby surfaces that continue to collapse into the same mixed cell.

This extension is not intended for ordinary terrain, exterior building
scouting, or routine camera placement. It provides only an eight-to-one voxel
aggregation and can approach the token and computation cost of a raw bounded
block observation. It must therefore have:

- the stricter Section 8 region, result-cell, and response limits;
- an explicit capability advertisement separate from ordinary cell sizes;
- the required size-4 `refines_map_id` and volume `fallback_reason`; and
- acceptance evidence that normal scenarios stop at cell size 4 or larger.

The `2x2x2` response still uses conservative occupancy: one-block geometry must
remain mixed rather than disappearing. Cell size `1` is not included as a
further refinement. If exact block inspection is ever required for validation,
it belongs in a small targeted block query rather than the spatial overview.

## 8. Response size and work limits

Response size and computation must be bounded independently.

Limiting only the number of returned aggregate cells is insufficient because a
small result can still require examining millions of underlying block columns
or voxels. The implementation needs both:

- a maximum returned-cell/node/run budget; and
- a maximum underlying column/voxel work budget.

The initial contract uses the following limits:

| Query class | Max aggregate cells | Max underlying extent/work | Max axis span | Max JSON response |
| --- | ---: | ---: | ---: | ---: |
| Ordinary surface (`4..32`) | 4,096 | 262,144 X/Z columns | 2,048 blocks X or Z | 256 KiB |
| Ordinary volume (`4..32`) | 4,096 | 2,097,152 logical voxels | 256 blocks per axis | 256 KiB |
| Surface fallback (`2x2`) | 512 | 2,048 X/Z columns | 64 blocks X or Z | 64 KiB |
| Volume fallback (`2x2x2`) | 512 | 4,096 logical voxels | 32 blocks per axis | 64 KiB |

Ordinary workflow guidance targets at most 1,024 aggregate cells even though
the hard contract permits 4,096. Requested-to-effective bounds expansion counts
against all limits. A request exceeding any applicable limit is rejected before
scanning with `query_too_large` and returns a suggested larger cell size, tiled
bounds, or reduced Y range.

These numbers are the initial release contract, not values independently copied
through the codebase. The mod advertises them, the sidecar validates against the
advertisement, and profiling may justify a later versioned/capability change.

The primary model-facing result should remain readable structured data. Opaque
base64 blobs, compressed binary grids, or bitsets may be useful as secondary
artifacts for non-model consumers, but they should not be the only way an agent
can understand coordinates.

## 9. Runtime and threading considerations

Minecraft state must be accessed on the appropriate client thread. Large scans
must not create visible frame stalls.

The implementation should use:

- native/chunk cached heightmaps for compatible surface requests;
- chunk-section non-empty counts or palette summaries for aligned volume cells;
- skipping known-empty chunk sections;
- time-sliced work with a target of at most 2 ms and a hard stop/reschedule at
  5 ms of spatial-sampler client-thread work per tick;
- cancellation and deadline checks between slices; and
- off-thread JSON assembly after immutable primitive samples have been captured.

Scans may span multiple ticks. Every response returns `capture_start_tick`,
`capture_end_tick`, and `consistency: "single_tick" | "multi_tick"`. A
multi-tick result is explicitly best-effort and never claims to be an atomic
snapshot. The initial contract has no `require_single_tick` option. Paused
replay worlds are stable at one replay time, while live-world results still
report their actual tick range.

The sampler should be a focused Minecraft-side component rather than adding
more large nested loops directly to `MinecraftBridgeAdapter`.

## 10. Capability negotiation and compatibility

The mod should advertise a spatial-observation capability containing enough
information for the sidecar to validate a request before calling the bridge.
The initial capability includes:

```json
{
  "spatial_map": {
    "surface": true,
    "volume": true,
    "loaded_chunks_only": true,
    "surface_cell_sizes": [4, 8, 16, 32],
    "surface_fallback_cell_sizes": [2],
    "volume_cell_sizes": [4, 8, 16, 32],
    "volume_fallback_cell_sizes": [2],
    "surface_modes": ["world_surface", "motion_blocking_no_leaves"],
    "default_surface_mode": "motion_blocking_no_leaves",
    "material_mix_limits": [1, 2, 3],
    "ordinary_target_cells": 1024,
    "ordinary_max_result_cells": 4096,
    "fallback_max_result_cells": 512,
    "max_response_bytes": 262144,
    "fallback_max_response_bytes": 65536,
    "partial_coverage": true,
    "multi_tick": true
  }
}
```

The detailed surface/volume source-work and axis limits from Section 8 are also
advertised in nested limit objects; the abbreviated example above avoids
duplicating the full table.

`observation.spatial_map` is an additive, capability-gated method in
`replay-mcp.bridge/1`. The existing status schema permits additional capability
properties, but shared schemas, fixtures, Java tests, TypeScript tests, and both
packaged protocol copies must still be updated together. An older mod produces
typed `capability_unavailable` at the public sidecar boundary rather than an
unknown-method surprise or misleading empty map.

## 11. Proposed errors and partial results

Expected typed failures or result states include:

- invalid or inverted bounds;
- bounds outside valid build height;
- unsupported cell size or surface mode;
- query too large, with a suggested cell size or maximum bounds;
- no active client world;
- unsupported active mode;
- capability unavailable;
- no loaded coverage;
- deadline or cancellation; and
- internal sampling failure.

Partially unloaded bounds produce a successful partial result by default
with explicit coverage. Unavailable cells must not be omitted in a way that
makes them indistinguishable from empty space.

## 12. Agent workflow policy

Adding a tool alone will not solve the observed behavior. The Replay Director
instructions currently permit `game_observe`, `game_query`, and additional
views during scouting. Without a stronger decision rule, an agent may continue
capturing many screenshots out of habit.

The intended workflow should be documented in the relevant operational and
cinematography skills:

```text
surface map at cell size 16 or 32
    -> identify the structure and broad open camera regions
surface map at cell size 4 or 8
    -> select a plausible bounded camera region
volume map at cell size 4 or larger, only when vertical geometry requires it
    -> distinguish ceilings, voids, platforms, overhangs, or hollow structures
one or a small number of screenshots
    -> place and visually refine the actual camera pose by several blocks
collision/range validation
    -> verify that the accepted camera is usable
```

Use a resolution-level-2 fallback only when a bounded size-4 result still cannot
resolve a tight ambiguity that matters to the shot. Use `2x2` for unresolved
surface relationships and `2x2x2` for unresolved volume geometry. Their
availability is not a reason to refine every successful query to size 2.

Use volume mode when:

- the active dimension or environment has ceilings/caverns;
- the requested structure is floating, hollow, inverted, stacked, or heavily
  overhung;
- surface statistics show mixed materials or strong relief that remains
  ambiguous after refinement;
- a screenshot or exact query directly conflicts with the surface model; or
- camera collision/line-of-sight behavior cannot be explained by the surface
  map.

Do not call volume mode automatically for every ordinary Overworld location.
It must not become a new default token sink.

The map is evidence for locating and refining geometry. It is not permission to
modify the world, and it does not override authoritative coordinates or scene
facts supplied by the user.

## 13. Explicit non-goals

This proposal does not attempt to provide:

- a replacement for screenshots or rendered-frame acceptance;
- automatic `natural` versus `constructed` classification;
- automatic building recognition or semantic labels such as castle, house, or
  road;
- a complete server-side world map;
- chunk generation or forced chunk loading;
- per-block spatial-map precision as a routine camera-scouting step;
- navigation safety guarantees;
- automatic camera-path authoring;
- arbitrary unbounded voxel export;
- a general-purpose Minecraft world editor; or
- authorization for teleportation, block changes, commands, or other world
  mutations.

## 14. Acceptance criteria

### 14.1 Contract and automated coverage

Automated tests should cover:

- shared Java/TypeScript acceptance and rejection of the same bridge fixtures;
- capability negotiation and unsupported older-mod behavior;
- positive and negative coordinates;
- bounds and world-grid alignment;
- each supported cell size;
- separate validation of the exceptional `2x2` and `2x2x2` capabilities and
  their stricter bounds;
- Y-range behavior and build-height boundaries;
- deterministic grid ordering and coordinate mapping;
- complete, empty, partial, and unavailable coverage;
- no chunk-loading side effects;
- response and work-limit enforcement;
- cancellation and deadlines; and
- palette indices, dominant shares, and optional material mixes.

Surface aggregation fixtures should include:

- flat terrain;
- a hill or cliff;
- a narrow tower inside a coarse cell;
- grass plus stone-brick mixed surface;
- water, foliage, decorative blocks, slabs, and snow layers; and
- a requested Y band beneath a higher surface.

Volume fixtures should include:

- a Nether-style floor, void, and ceiling;
- a one-block-thick floating grass platform;
- a reversed grass-covered pyramid;
- a hollow building;
- a thin bridge or wall;
- disconnected occupied volumes in one region;
- fluids; and
- partially unloaded chunks.

At coarse resolution, thin or disconnected geometry may lose exact shape, but
its existence must not disappear. It must remain represented by a mixed or
otherwise occupied aggregate that the agent can refine.

Workflow coverage should also verify that ordinary exterior and terrain tasks
stop at cell size 4 or larger. Dedicated fine-surface and tight-volume fixtures
should prove that the `2x2` and `2x2x2` fallbacks work when justified. A
fallback fails its product goal if agents routinely invoke it on ordinary
scenes without improving final camera acceptance.

### 14.2 Performance acceptance

Performance acceptance records:

- client-thread time per scan or per scan slice;
- end-to-end latency for representative loaded regions;
- serialized response size;
- returned cell/run count;
- underlying columns or voxels examined;
- cancellation responsiveness; and
- frame-time impact while the world is live.

The initial release gates are:

- ordinary surface p95 end-to-end latency at or below 150 ms;
- ordinary volume p95 at or below 500 ms;
- level-2 fallback p95 at or below 250 ms for its stricter region limits;
- no accepted query above 2 seconds in the representative suite;
- spatial-sampler client-thread work at or below 2 ms p95 per tick and no
  attributable slice above the 5 ms reschedule boundary;
- typical responses at or below 64 KiB and every response within its Section 8
  hard limit; and
- zero newly loaded chunks caused by the query.

These gates are evaluated on the documented fixture hardware/configuration and
reported with that environment. A slower unsupported machine may take longer,
but exceeding the work, response, or chunk-loading limits is always a failure.

### 14.3 Live acceptance

A live acceptance pass should:

1. connect through the real sidecar and Fabric bridge;
2. query known terrain and structures without acquiring the control lease;
3. verify that no new chunks are loaded because of the query;
4. correlate returned cell bounds, heights, occupancy, and materials with known
   Minecraft coordinates;
5. cover at least one ordinary surface scene and the complex volume fixtures
   above where practical;
6. refine a coarse result only far enough to select a plausible camera region;
7. use a small number of screenshots to choose and verify the actual camera
   pose; and
8. record failures, timings, payload sizes, and observed frame impact.

Product-level acceptance should demonstrate that the updated workflow finds a
usable, visually accepted camera pose with materially fewer scouting screenshots
and less observation context than the existing image-first approach. Exact
agreement with one predetermined camera coordinate is not required because
multiple poses may satisfy the shot.

### 14.4 Agent-efficiency benchmark

Tool correctness and tool latency are necessary but do not prove that the
feature saves agent time or model context. The end-to-end benchmark should run
the same camera-scouting tasks under three conditions:

| Condition | Available capability | Workflow guidance |
| --- | --- | --- |
| Baseline | Existing observations and queries | Existing image-first behavior |
| Tool only | Spatial map available | Existing guidance |
| Complete change | Spatial map available | Structured-first camera scouting |

The tool-only condition distinguishes adoption problems from primitive value.
The complete-change condition measures the intended product behavior.

Each paired run should use the same model and settings, a fresh context, the
same prompt, and an identical world/replay state, player/camera start, render
distance, loaded chunks, and target shot. The task prompt should not name the
tool or impose an artificial screenshot limit. Screenshot reduction is an
outcome to measure, not a hint given only to the new condition.

Run separate agent suites for:

- surface-sufficient exterior/terrain scenes;
- volume-required Nether, floating, hollow, inverted, or overhung scenes; and
- a mixed held-out routing suite in which the agent must decide whether surface
  information is sufficient.

Example surface task:

> Scout the supplied region and choose a static exterior camera pose that shows
> the complete building from a clear three-quarter angle. The building should
> not be clipped by terrain and should occupy a useful portion of the frame. Do
> not modify the world. Return the final camera pose and final observation.

Example volume task:

> Choose a camera pose inside the supplied Nether chamber that shows the floor,
> ceiling architecture, and central structure without intersecting geometry or
> losing the subject behind an obstruction. Do not modify the world. Return the
> final camera pose and final observation.

The benchmark harness, rather than the agent, should record:

- model input tokens including vision tokens, output tokens, and cached tokens
  where the runtime exposes them;
- total wall-clock time from prompt to accepted result;
- screenshot count and dimensions;
- ordinary surface/volume and `2x2`/`2x2x2` fallback call counts;
- per-tool end-to-end latency and response bytes;
- Minecraft-side sampling time, returned cells/runs, and underlying work;
- collision/range validation outcome; and
- blinded visual acceptance of the final shot.

The bridge cannot know the model's token use. Exact token-saving claims require
usage telemetry from the agent/API runtime. Serialized bytes and image counts
are useful proxies when exact usage is unavailable, but must not be reported as
exact token totals.

The repository includes `tools/evaluate_spatial_benchmark.py` and its JSONL
format reference to validate pairing, trial counts, full-attempt cost per
accepted shot, fallback routing, and the gates below. The runner that invokes
the agent remains environment-specific and must write actual runtime usage; the
evaluator deliberately leaves the token gate unevaluable when vision-inclusive
usage is absent.

Report success rate separately and use cost per successful task so failures and
retries are not hidden:

```text
tokens per successful task = total tokens across all attempts / accepted shots
time per successful task   = total elapsed time across all attempts / accepted shots
```

The level-2 fallbacks have an additional routing criterion: ordinary surface
and exterior tasks should almost never invoke either one. Deliberately fine
surface and tight-volume fixtures should demonstrate whether `2x2` improves on
stopping at `4x4` and whether `2x2x2` improves on stopping at `4x4x4`. If a
fallback is routinely selected or does not improve the final shot, the workflow
or fallback contract has failed even if the primitive itself is technically
correct.

Run at least ten fresh-context trials per scenario and freeze the baseline before
evaluating the completed change. The product gates are:

- accepted-shot rate and blinded visual acceptance no more than five percentage
  points below baseline;
- at least 30 percent fewer model input tokens per accepted shot;
- at least 25 percent less wall-clock time per accepted shot;
- at least 50 percent fewer scouting screenshots; and
- level-2 fallbacks used in no more than 10 percent of ordinary-scene runs while
  demonstrably resolving the dedicated fine-surface and tight-volume fixtures.

The token gate cannot be marked passed when the agent/API runtime does not
provide vision-inclusive usage telemetry. Savings must be demonstrated over the
full task, not inferred from one small tool response.

## 17. Closed decision record

The initial implementation scope closes the former open decisions as follows:

1. **Public and bridge naming:** use `game_query(kind: "spatial_map")` with
   `representation: "surface" | "volume"`, backed by
   `observation.spatial_map`. Do not add top-level heightmap/voxel tools.
2. **Surface predicates:** support `motion_blocking_no_leaves` as the default
   and `world_surface` as the optional visible-silhouette mode, following native
   Minecraft predicate semantics.
3. **Y-range semantics:** find the topmost qualifying block inside the requested
   half-open Y range. Use a cached heightmap only when equivalent; never clamp a
   global height into the requested band.
4. **Coordinates and alignment:** use integer half-open bounds, expand outward
   to world-origin multiples of `cell_size` with correct negative floor
   division, return requested/effective bounds, and use fixed increasing
   Z/X/Y traversal orders from Section 5.
5. **Limits:** use the concrete ordinary/fallback cell, source-work, axis, and
   response limits in Section 8, with a 1,024-cell ordinary workflow target and
   typed preflight rejection above hard limits.
6. **Default material:** always return dominant surface material/share and
   dominant exposed volume material/share when an exposed face exists.
7. **Material refinement:** `material_mix_limit` is `1 | 2 | 3`, defaults to
   `1`, and returns top-two/top-three composition only when requested.
8. **Exposed volume material:** count six-direction faces adjacent to a
   non-solid neighbor, inspect only a loaded one-block halo, exclude unknown
   halo faces, and weight shares by exposed face area.
9. **Volume encoding:** use ordered absolute-coordinate vertical runs with
   implicit loaded-empty intervals and explicit unavailable boxes; do not use a
   dense 3D array, unordered voxel tuples, or octree in the initial contract.
10. **Partial coverage:** return explicit partial results by default;
    `require_complete: true` produces `outside_loaded_area` when any requested
    coverage is unavailable.
11. **Consistency:** allow time-sliced multi-tick scans, return capture tick
    range and `single_tick`/`multi_tick`, and provide no atomic/single-tick
    requirement option initially.
12. **Runtime modes:** support live idle/recording and paused loaded replay;
    reject playing replay with `replay_must_be_paused` and reject loading or
    rendering modes.
13. **Performance and product gates:** use the primitive latency/frame budgets
    in Section 14.2 and the token, time, screenshot, and acceptance thresholds
    in Section 14.4.
14. **Level-2 fallbacks:** require a containing size-4 `refines_map_id`, a
    representation-specific enumerated `fallback_reason`, the strict Section 8
    limits, separate capability fields, audit telemetry, and routing acceptance
    that keeps them out of at least 90 percent of ordinary runs.

No contract decisions remain open in this scoping document. Implementation may
discover a concrete incompatibility, but changing one of these decisions then
requires an explicit architecture revision with evidence rather than an
unrecorded implementation choice.

## 18. Finalized scope summary

The initial implementation contract is:

- add one capability-gated, read-only `game_query` spatial-map kind;
- support cheap `surface` and fallback `volume` representations;
- use cell sizes 4, 8, 16, and 32 for the ordinary workflow;
- support surface cell size 2 only as a stricter, explicitly exceptional
  fallback for unresolved fine surface relationships;
- support volume cell size 2 only as a stricter, explicitly exceptional
  fallback for unresolved tight volume geometry;
- exclude cell size 1 from the initial spatial-map scope;
- return surface minimum/mean/maximum rather than average alone;
- return dominant surface block plus its share using a compact palette;
- never infer `natural` versus `constructed` in the protocol;
- make volume aggregation conservative so thin geometry cannot disappear;
- encode volume results sparsely with absolute coordinate bounds;
- enforce both response-size and underlying-work budgets;
- inspect loaded chunks only and represent missing data explicitly;
- support live idle/recording worlds and paused loaded replays;
- update agent workflow guidance so structured scouting precedes screenshots;
- stop structured refinement once the map identifies a sufficient camera region
  rather than pursuing per-block coordinates; and
- retain screenshots for visual refinement and actual acceptance.

This summary remains the governing implementation contract. The bridge,
sidecar, schemas, automated checks, and structured-first workflow guidance are
implemented as of 2026-09-23. A real Minecraft 26.2 run has also passed nearby
surface and volume sampling, explicit partial/unavailable coverage, repeated
non-loading distant probes, visual correlation, and the public sidecar
`game_query` route. Sections 14.2 through 14.4 still contain outstanding
acceptance work: the representative p95/frame-time suite, complex volume
fixtures, and ten-trial-per-scenario agent-efficiency gates must not be inferred
from this smoke run.
